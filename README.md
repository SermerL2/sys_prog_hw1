## Реализация L1-нормы

Реализация представленна в файле [matrix_l1_norm.cpp](/src/matrix_l1_norm.cpp). Для сборки используется скрипт [build.sh](/scripts/build.sh). При помощи аргументов можно:

- Выбирать метод подсчета L1-нормы
  1. `row` - проход по строкам
  2. `col` - проход по столбцам
  3. `nop` - нет прохода (нужен для вычисления промахов кэша, не связанных с различиями методов)
- Изменять размер матрицы: `default = 4096`

## Расчёт кэш-линий и «бесполезного» трафика

Размер кэш линии для CPU AMD Ryzen 7 7700: 64 байта. *Подтверждается в [Software Optimization Guide for the AMD Zen4 Microarchitecture](https://www.numberworld.org/blogs/2024_8_7_zen5_avx512_teardown/57647_zen4_sog.pdf) в разделе 2.2 (открывается только с VPN).* Также, в Linux можно проверить размер кэш линии с помощью вывода `/proc/cpuinfo`: `cache_alignment : 64`.

### Row-major (оптимальный)

Тк применяется тип данных `uint64_t`, то в 1 кэш линию помещается 64 / 8 = 8 элементов матрицы.

Всего данных: N² = 4096² = `16_777_216` (test sample size)
Теоретическое количество кэш-линий, занимаемых матрицей: N² / 8 = `2_097_152`.

При оптимальном проходе проход по матрице является последовательным, и теоретически должно произойти `2_097_152` промахов кэша. Однако реальное значение промахов составило `6_293_304`. Данное значение можно объяснить подготовительными операциями процессора до выполнения функций вычисления L1 нормы. Это наглядно показывют метрики для `NOOP`. Получим чистый L1-dcache-load-misses:

```
L1-dcache-load-misses = 6_293_304 - 4_194_649 = 2_098_655
```

Полученное значение считанных из памяти кэш линий = `2_098_655` почти иделально совпадает с теоретическим = `2_097_152`.

### Column-major (неоптимальный)

Начнем с теоретического рассчета. Тк размер кэша < размера линии матрицы (64 < 4096 * uint64_t), то при каждом чтении кэша, будет попадать только 1 нужное значение, а значит требуется считать каждый элемент из памяти по отдельности. Отсюда, теоретическое количество обращений в память = 4096² = `16_777_216`.

Реальное количество промахов кэша составило `21_105_225`, вычтим `NOOP` промахи:

```
L1-dcache-load-misses = 21_105_225 - 4_194_649 = 16_920_576
```
Полученное значение считанных из памяти кэш линий = `16_920_576` почти иделально совпадает с теоретическим = `16_777_216`.

### Расчет лишнего трафика

- Разница в количестве загруженных линий:

```
21 105 225 – 6 291 545 = 14 813 680 линий
```

- Объём лишнего трафика:

```
14 813 680 × 64 байта = 948 075 520 байт ≈ 904 МБ
```

## Выводы

1. Пространственная локальность критически важна для производительности на современных процессорах с иерархической памятью.
2. Последовательный проход оказался оптимальным решением, тк каждая загрузка данных в кэш давала 64 байта полезной нагрузки, в то время как обход по столбцам на каждую загрузку кэша получал только 8 байт полезных данных, из-за чего потребовалось увеличение количества обращений в память в 8 раз `(2_098_655 против 16_920_576)`. Также оказались лучше следующие параметры:
- L1-dcache-load-misses: `6_293_304 против 21_105_225`, лучше в 3.35 раза
- IPC: `2.83 против 0.64`, лучше в 4.4 раза
- Time elapsed: `0.080 с против 0.136 с`, лучше в 1.7 раза
