## Теоретические расчеты

Размер кэш линии для CPU AMD Ryzen 7 7700: 64 байта. *Подтверждается в [Software Optimization Guide for the AMD Zen4 Microarchitecture](https://www.numberworld.org/blogs/2024_8_7_zen5_avx512_teardown/57647_zen4_sog.pdf) в разделе 2.2 (открывается только с VPN).* Также, в Linux можно проверить размер кэш линии с помощью вывода `/proc/cpuinfo`: `cache_alignment : 64`.

### Column-major (неоптимальный)

Тк размер кэша < размера линии матрицы (64 < 4096 * uint64_t), то при каждом чтении кэша, будет попадать только 1 нужное значение, а значит требуется считать каждый элемент из памяти по отдельности. Отсюда, теоретическое количество обращений в память = 4096² = `16 777 216`.

### Row-major (оптимальный)

Тк применяется тип данных `uint64_t`, то в 1 кэш линию помещается `64 / 8 = 8` элементов матрицы.

Всего данных: N² = 4096² = `16 777 216` (test sample size)
Теоретическое количество кэш-линий, занимаемых матрицей: N² / 8 = `2 097 152`.

Таким образом, оптимальный метод оказывается эффективнее в плане промахов кэша в `8` раз.

### Бесполезный трафик

```
Column-major: (16 777 216 − 2 097 152) × 64 байт
            = 14 680 064 × 64
            = 939 524 096 байт ≈ 896 МБ
```

| Метрика                          | Row-major  | Column-major |
|----------------------------------|------------|--------------|
| Обращений к элементам            | 16 777 216 | 16 777 216   |
| Полезные элементы в кэш-линии    | 8 из 8     | 1 из 8       |
| Полезно использованных кэш-линий | 2 097 152  | 2 097 152    |
| Фактически загруженных кэш-линий | 2 097 152  | 16 777 216   |
| L1-dcache-load-misses (теор.)    | 2 097 152  | 16 777 216   |
| Полезный трафик, МБ              | 128        | 128          |
| «Бесполезный» трафик, МБ         | 0          | **896**      |
| Отношение промахов col/row       | 1×         | **8.0×**     |

### Временной анализ одного прохода

| Метод        | Мин. время одного прохода (с) | Относительно row-major |
|--------------|-------------------------------|------------------------|
| Row-major    | 0.003757                      | 1.0×                   |
| Column-major | 0.073891                      | **19.7×**              |
| NOOP         | ~5·10⁻¹⁰                      | ~0                     |

По сравнению с первой версией HW *(можно посмотреть в истории коммитов)*, разница составила `19.7` раз против `1.7`, что явно указывает на некорректность предыдущих изменений.

*P.S. NOOP-замер показывает только накладные расходы цикла замера и не используется для вычитания, так как время row/column измеряется внутри программы без учёта старта*

Оптимальный метод Row-major оказывается эффективнее по всем показателям:

- Преимущество по промахам кэша совпала с теоретическим расчетам: в `8` раз лучше.
- IPC оказалось в `15.27` раз эффективнее. При этом количество инструкций отличается не сильно, что означает bottleneck из-за частого обращения в память.

### Бесполезный трафик

